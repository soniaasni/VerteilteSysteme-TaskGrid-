\section{Namensdienst und Worker-Management}
\label{sec:namensdienst}

\subsection{Service Discovery -- Konzept}

Der Namensdienst (\emph{Naming Service}) implementiert die Service-Discovery-Komponente von TaskGrid+.
Seine Aufgabe besteht darin, alle aktiven Worker zu verwalten und dem Dispatcher auf Anfrage mitzuteilen, welche Worker für einen bestimmten Task-Typ aktuell verfügbar sind.
\\
Ohne den Namensdienst müssten Worker-Adressen statisch im Dispatcher hinterlegt werden.
Dynamisches Hinzufügen, Entfernen oder Skalieren von Workern während der Laufzeit wäre dadurch nicht möglich.
Stattdessen folgt TaskGrid+ dem folgenden Prinzip:

\begin{itemize}
	\item \textbf{Worker registrieren sich selbst}: Jeder Worker meldet sich beim Start beim Namensdienst an.
	\item \textbf{Worker senden Heartbeats}: Die Verfügbarkeit wird kontinuierlich durch regelmäßige Heartbeat-Nachrichten überwacht.
	\item \textbf{Dispatcher fragt bei Bedarf ab}: Vor jedem Dispatch-Vorgang wird der Namensdienst nach verfügbaren Workern gefragt.
	\item \textbf{Keine statische Adresskonfiguration}: Worker-Adressen erscheinen weder im Dispatcher-Code noch in Konfigurationsdateien.
\end{itemize}
Der Namensdienst fungiert damit als zentrale Instanz für die Verwaltung aller verfügbaren Worker und stellt die Entkopplung zwischen Dispatcher und Workern sicher.

\subsection{Speicherung und Verwaltung von Worker-Informationen}

Gemäß Aufgabenstellung speichert der Namensdienst alle Worker-Registrierungen ausschließlich im Arbeitsspeicher.
Eine Persistenzschicht in Form einer Datenbank oder Datei existiert nicht.
\\
Jeder registrierte Worker wird durch eine interne \texttt{Worker}-Instanz repräsentiert.
Gespeichert werden unter anderem:

\begin{itemize}
	\item eindeutige \texttt{worker\_id}
	\item unterstützte \texttt{task\_types}
	\item Netzwerkadresse und Port
	\item aktueller Status (\texttt{ACTIVE}, \texttt{UNHEALTHY}, \texttt{OFFLINE})
	\item Zeitpunkt des letzten Heartbeats
	\item aktuelle Auslastung (\texttt{current\_load})
\end{itemize}
Unterstützt ein Worker mehrere Task-Typen, erzeugt der Namensdienst für jeden Task-Typ einen eigenen Eintrag.
Dadurch kann die Worker-Suche später als einfache Filteroperation über den gewünschten Task-Typ durchgeführt werden.
Die ausschließliche Speicherung im Arbeitsspeicher wurde bewusst gewählt:

\begin{itemize}
	\item keine zusätzliche Infrastruktur erforderlich
	\item automatische Bereinigung veralteter Einträge durch Heartbeats
	\item vereinfachte Skalierung neuer Worker
	\item automatische Wiederherstellung durch erneute Registrierung beim Start
\end{itemize}

\subsection{Worker-Registrierung}

Jeder Worker registriert sich unmittelbar nach dem Start beim Namensdienst.
Die Registrierung erfolgt über den gRPC-Aufruf \texttt{RegisterWorker}.

\begin{lstlisting}[language=Python,caption={Worker-Registrierung (worker.py)}]
	stub.RegisterWorker(
	taskgrid_pb2.RegisterWorkerRequest(
	message_type="REGISTER_WORKER",
	request_id=str(uuid.uuid4()),
	timestamp=int(time.time()),
	sender=WORKER_ID,
	payload=taskgrid_pb2.RegisterWorkerRequest.Payload(
	worker_id=WORKER_ID,
	task_types=TASK_TYPES,
	address=WORKER_HOST,
	port=WORKER_PORT,
	status="ACTIVE",
	current_load=get_current_load(),
	)
	)
	)
\end{lstlisting}

Die Identität eines Workers wird über mehrere Umgebungsvariablen definiert:

\begin{itemize}
	\item \texttt{WORKER\_HOST}: Docker-Service-Name des Containers (z.,B. \texttt{worker-sum})
	\item \texttt{TASK\_TYPES}: unterstützte Task-Typen
	\item \texttt{WORKER\_ID}: eindeutige Instanz-ID im Format \texttt{worker-<typ>-<hostname>}
\end{itemize}
Dadurch erhält jede Worker-Instanz auch bei horizontaler Skalierung eine eindeutige Identität.
\\
Auf Seiten des Namensdienstes wird jede Registrierung validiert und idempotent verarbeitet.
Existierende Einträge mit derselben Worker-ID werden zunächst entfernt und anschließend neu angelegt.
Dadurch können sich Worker nach einem Neustart gefahrlos erneut registrieren, ohne doppelte Einträge zu erzeugen.

\subsection{Heartbeat-Mechanismus}

Nach erfolgreicher Registrierung startet jeder Worker einen separaten Heartbeat-Thread.
Dieser sendet in festen Zeitabständen Heartbeat-Nachrichten an den Namensdienst.

\begin{lstlisting}[language=Python,caption={Heartbeat-Loop (worker.py)}]
	def send_heartbeat_loop():
	while True:
	stub.SendHeartbeat(
	taskgrid_pb2.HeartbeatRequest(
	message_type="HEARTBEAT",
	sender=WORKER_ID,
	timestamp=int(time.time()),
	request_id=str(uuid.uuid4()),
	payload=taskgrid_pb2.HeartbeatRequest.Payload(
	worker_id=WORKER_ID,
	current_load=get_current_load()
	)
	)
	)
	time.sleep(HEARTBEAT_INTERVAL)
\end{lstlisting}

Neben der Worker-ID wird auch die aktuelle Auslastung (\texttt{current\_load}) übertragen.
Dadurch kennt der Namensdienst jederzeit den aktuellen Zustand aller registrierten Worker.

Die relevanten Parameter sind über Umgebungsvariablen konfigurierbar:

\begin{table}[H]
	\centering
	\begin{tabular}{l c}
		\toprule
		Parameter & Standardwert \\
		\midrule
		\texttt{HEARTBEAT\_INTERVAL\_SECONDS} & 5 s \\
		\texttt{NAMESERVICE\_UNHEALTHY\_SECS} & 10 s \\
		\texttt{NAMESERVICE\_OFFLINE\_MULT} & 2 \\
		\bottomrule
	\end{tabular}
	\caption{Heartbeat-Konfiguration}
\end{table}

\subsection{Erkennung inaktiver Worker}

Der Namensdienst überwacht kontinuierlich alle registrierten Worker.
Ein Hintergrundthread prüft in regelmäßigen Abständen den Zeitpunkt des letzten empfangenen Heartbeats.
\\
Bleibt ein Heartbeat länger als \texttt{NAMESERVICE\_UNHEALTHY\_SECS} aus, wird der Worker als \texttt{UNHEALTHY} markiert.
\\
Bleibt der Heartbeat länger als

\noindent [\texttt{NAMESERVICE\_UNHEALTHY\_SECS} \times \texttt{NAMESERVICE\_OFFLINE\_MULT}]

\noindent aus, wird der Worker als \texttt{OFFLINE} betrachtet und aus der internen Registry entfernt.
Die Zustandsübergänge lauten:

\begin{center}
	ACTIVE $\rightarrow$ UNHEALTHY $\rightarrow$ OFFLINE
\end{center}
Worker mit Status \texttt{UNHEALTHY} oder \texttt{OFFLINE} werden vom Namensdienst nicht mehr an den Dispatcher zurückgegeben.
Dadurch können ausgefallene Worker automatisch aus dem System entfernt werden, ohne dass ein manueller Eingriff erforderlich ist.

\subsection{Worker-Deregistrierung}

Beim regulären Herunterfahren eines Workers wird eine explizite Deregistrierung durchgeführt.

\begin{lstlisting}[language=Python,caption={Graceful Shutdown (worker.py)}]
	def deregister_worker():
	stub.DeregisterWorker(
	taskgrid_pb2.DeregisterWorkerRequest(
	message_type="DEREGISTER_WORKER",
	request_id=str(uuid.uuid4()),
	timestamp=int(time.time()),
	sender=WORKER_ID,
	payload=taskgrid_pb2.DeregisterWorkerRequest.Payload(
	worker_id=WORKER_ID,
	)
	)
	)
\end{lstlisting}
Dadurch wird der Worker unmittelbar aus der Registry entfernt und muss nicht erst durch den Heartbeat-Timeout erkannt werden.
Dies reduziert die Zeit bis zur Entfernung eines Workers und unterstützt einen kontrollierten (\emph{graceful}) Shutdown.

\subsection{Dispatcher-seitiger Namensdienst-Client}

Der Dispatcher kommuniziert über den \texttt{NamensdienstClient} mit dem Namensdienst.
Die Verbindungsadresse wird ausschließlich aus Umgebungsvariablen gelesen:

\begin{lstlisting}[language=Python,caption={NamensdienstClient-Konfiguration}]
	host = os.environ.get("NAMENSDIENST_HOST", "namensdienst")
	port = os.environ.get("NAMENSDIENST_PORT", "50052")
	self._target = f"{host}:{port}"
\end{lstlisting}
Vor jedem Dispatch-Vorgang fragt der Dispatcher den Namensdienst über \texttt{LookupWorker} nach verfügbaren Workern des benötigten Task-Typs.
Bei Kommunikationsfehlern oder Nichterreichbarkeit des Namensdienstes wird keine Exception propagiert.
Stattdessen wird eine leere Liste zurückgegeben, sodass der Dispatcher den Task nach einer Wartezeit erneut einplant.

\begin{lstlisting}[language=Python,caption={Fehlertoleranter Worker-Lookup}]
	try:
	response = self._stub.LookupWorker(...)
	except grpc.RpcError:
	return []
\end{lstlisting}

\subsection{Worker-Auswahlstrategie}

Liefert der Namensdienst mehrere geeignete Worker zurück, erfolgt die Auswahl über einen thread-sicheren Round-Robin-Algorithmus.

\begin{lstlisting}[language=Python,caption={Round-Robin-Selektion}]
	class RoundRobinSelector:
	def select(self, task_type, workers):
	if not workers:
	return None
	
	```
	with self._lock:
	idx = self._counters[task_type] % len(workers)
	self._counters[task_type] += 1
	
	return workers[idx]
	```
	
\end{lstlisting}
Für jeden Task-Typ wird ein eigener Zähler geführt.
Dadurch werden aufeinanderfolgende Aufgaben gleichmäßig auf alle verfügbaren Worker verteilt.
Beispielsweise ergibt sich bei drei registrierten \texttt{worker-sum}-Instanzen folgende Verteilung:

\noindent [
0 \rightarrow 1 \rightarrow 2 \rightarrow 0 \rightarrow 1 \rightarrow 2
]

\noindent Die Strategie ist einfach, deterministisch und gewährleistet eine gleichmäßige Lastverteilung ohne zusätzlichen Kommunikationsaufwand.

\subsection{Skalierung}

Durch die Kombination aus Service Discovery und Docker Compose können Worker-Typen unabhängig voneinander skaliert werden.

\begin{lstlisting}[language=bash,caption={Skalierungsbeispiel}]
	docker compose up 
	--scale worker-sum=3 
	--scale worker-reverse=2
\end{lstlisting}
Jede Instanz registriert sich selbstständig beim Namensdienst und erhält eine eigene \texttt{WORKER\_ID}.
Der Dispatcher muss nicht angepasst werden.
Der Namensdienst liefert automatisch alle verfügbaren Instanzen zurück und der Round-Robin-Algorithmus verteilt eingehende Tasks gleichmäßig auf diese Worker.
Damit unterstützt TaskGrid+ horizontale Skalierung ohne Änderungen an Dispatcher, Client oder Namensdienst.
