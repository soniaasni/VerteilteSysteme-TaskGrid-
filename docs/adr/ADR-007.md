# ADR-007: Nebenläufigkeitsstrategie im Dispatcher (Issue #21)

**Status:** Akzeptiert  
**Issue:** #21  
**Datum:** 2026-05-26  
**Entscheider:** soniaasni, Xplosy, Elena7x

---

## Kontext

Prüfungsanforderung §19.3 verlangt: *„Mehrere Aufgaben und mehrere Worker sollen
parallel verarbeitet werden können, ohne inkonsistente Zustände zu erzeugen."*

Der Dispatcher ist ein multithreaded System: gRPC-Anfragen (PostTask, ReturnResult,
GetResult) werden in einem `ThreadPoolExecutor` des gRPC-Frameworks bedient, während
der Dispatch-Loop in einem eigenen Thread läuft und Timeout-Timer in weiteren
Threads feuern. Ohne explizite Synchronisation können Race Conditions entstehen.

Konkrete Gefahrenstellen:
- Zwei gRPC-Threads modifizieren gleichzeitig denselben Task (z.B. `ReturnResult`
  parallel zu einem Timeout-Callback).
- Der Dispatch-Loop liest Task-Status während ein gRPC-Thread ihn ändert.
- Mehrere Threads rufen gleichzeitig `new_task_id()` auf und erhalten dieselbe ID.
- `RoundRobinSelector` inkrementiert einen geteilten Zähler aus mehreren Threads.

---

## Entscheidung

**Gewählte Strategie: Fine-Grained Locking — ein Lock pro Datenstruktur**

Jede geteilte Datenstruktur schützt ihre Operationen selbst mit einem
`threading.Lock`. Kein globaler Dispatcher-Lock, keine lock-freien Strukturen,
kein Message-Passing-Modell. Konkret:

### 1. TaskStore — `threading.Lock` auf allen Methoden

```
add()         │
get()         │  alle unter self._lock
update()      │
all_tasks()   │
worker_load_map() │
```

`all_tasks()` und `worker_load_map()` erzeugen unter Lock einen Snapshot
(`list(...)` bzw. neues Dict), sodass der Aufrufer einen konsistenten Zustand
erhält, auch wenn danach weitere Änderungen stattfinden.

### 2. TaskQueue — `queue.Queue` aus der Python-Standardbibliothek

`queue.Queue` ist intern thread-sicher (GIL + internes Lock). Kein zusätzlicher
Lock nötig. `enqueue()` → `put()`, `dequeue()` → `get(timeout=...)`. Das
blocking `get` mit Timeout verhindert Busy-Waiting im Dispatch-Loop.

### 3. RoundRobinSelector — `threading.Lock` auf Zähler-Inkrementierung

```python
with self._lock:
    idx = self._counters[task_type] % len(workers)
    self._counters[task_type] += 1
```

Read-Modify-Write auf dem Zähler ist atomar. Ohne Lock könnte derselbe Index
zweimal vergeben werden (Lost Update), was Round-Robin-Fairness verletzt.

### 4. new_task_id() — `threading.Lock` auf globalem Zähler

```python
with _task_id_lock:
    _task_id_counter += 1
    return str(_task_id_counter)
```

Garantiert eindeutige, kollisionsfreie IDs auch bei gleichzeitigen PostTask-Aufrufen.

### 5. Dispatch-Loop — `ThreadPoolExecutor` für parallele Dispatches

Der Haupt-Loop dequeued sequenziell (ein Thread, kein Race auf `queue.get`).
Jeder Dispatch-Aufruf wird an den `ThreadPoolExecutor` (10 Worker-Threads)
übergeben. Mehrere Tasks können dadurch gleichzeitig an verschiedene Worker
gesendet werden, ohne dass sich die gRPC-Aufrufe blockieren.

### 6. Timeout-Timer — `threading.Lock` auf `_timers`-Dict

```python
with self._timers_lock:
    self._timers[task_id] = timer   # start
    timer = self._timers.pop(task_id, None)  # cancel
```

Verhindert Race zwischen Timer-Start (im Dispatch-Thread) und Timer-Cancel
(im ReturnResult-Thread).

### 7. Worker-Last (current_load) — hybride Verfolgung

Der Dispatcher verfolgt die aktive Last pro Worker lokal über `TaskStore.worker_load_map()`:
Gezählt werden alle Tasks im Zustand `DISPATCHED` oder `PROCESSING` mit gesetztem
`assigned_worker`-Feld. Diese Methode gibt einen konsistenten Snapshot unter Lock zurück.

Zusätzlich liefert der Namensdienst `current_load` aus dem letzten Heartbeat des
Workers. Der `RoundRobinSelector` verwendet derzeit die Namensdienst-Daten nicht
aktiv (Round-Robin ist load-unaware), aber `worker_load_map()` stellt die Daten
für das Monitoring (`GET /status`) und potenzielle spätere Erweiterungen bereit.

## Betrachtete Alternativen

### A: Globaler Dispatcher-Lock (Coarse-Grained Locking)

Ein einziger Lock für alle Operationen am Dispatcher-Zustand.

**Abgelehnt**, weil:
- Keine echte Parallelität: gRPC-Threads, Dispatch-Loop und Timer müssen alle
  serialisiert auf denselben Lock warten.
- gRPC-Framework bedient Anfragen in einem ThreadPoolExecutor — unter globalem
  Lock würde ein langsamer Request alle anderen blockieren.
- Deadlock-Risiko geringer als bei mehreren Locks, aber Performance zu schlecht.

### B: Lock-freie Datenstrukturen (z.B. `concurrent.futures`, atomare Operationen)

Verwendung von `queue.SimpleQueue`, `collections.deque` mit atomaren Operationen,
oder explizite CAS-Schleifen (Compare-And-Swap).

**Abgelehnt**, weil:
- In Python gibt es kein echtes Compare-And-Swap ohne Lock (GIL hilft nur bei
  einfachen Byte-Code-Operationen).
- `collections.deque` ist thread-sicher für `append`/`popleft`, aber nicht für
  zusammengesetzte Operationen (z.B. „read dann write").
- Komplexer zu verstehen, schwerer korrekt zu verifizieren — kein Vorteil gegenüber
  Lock-basiertem Ansatz in Python.

### C: Actor-Modell / Message Passing (z.B. `multiprocessing.Queue` zwischen Prozessen)

Jede Komponente läuft in einem eigenen Prozess, kommuniziert nur über Nachrichten.

**Abgelehnt**, weil:
- Python-Prozesse teilen keinen Speicher → TaskStore müsste serialisiert/deserialisiert
  werden (Pickle) bei jedem Zugriff.
- Erheblicher Overhead für ein System das im Studienkontext auf einer einzelnen
  Maschine läuft.
- Komplexe Fehlerbehandlung wenn Prozesse abstürzen.

### D: Async/Await mit asyncio

Alle Dispatcher-Komponenten als async, gRPC-Server als `grpc.aio`.

**Abgelehnt**, weil:
- `grpc.aio` erfordert vollständig async-kompatiblen Code — bestehender synchroner
  Code (TaskStore, Timer, WorkerClient) müsste komplett umgebaut werden.
- Async verhindert keine Race Conditions wenn blockierende Operationen in Threads
  gemischt werden.
- Kein Vorteil gegenüber Thread-basiertem Ansatz für I/O-gebundene gRPC-Aufrufe,
  die ohnehin im gRPC-eigenen ThreadPoolExecutor laufen.

### E: Gewählte Strategie (Fine-Grained Locking) ✓

- Ein Lock pro Datenstruktur → minimale Contention, maximale Parallelität.
- Jede Klasse ist selbst für ihre Thread-Sicherheit verantwortlich → klare
  Kapselung, einfach unit-testbar.
- Beweisbar korrekt: 13 Nebenläufigkeits-Tests mit 10–100 gleichzeitigen Threads.
- Python-idiomatisch: entspricht dem Vorgehen der Standardbibliothek (`queue.Queue`,
  `threading.Lock`).
- Kein Framework-Overhead, keine externen Abhängigkeiten.

## Konsequenzen

**Positiv:**
- Vollständige Parallelität: PostTask, ReturnResult, GetResult, Dispatch und
  Timeouts können gleichzeitig ablaufen ohne Blocking.
- Korrektheit bewiesen durch automatisierte Stress-Tests.
- Verständlich: Standard-Python-Primitives, kein Framework-Wissen nötig.

**Negativ:**
- Lock-Contention bei sehr hohem Durchsatz auf `TaskStore` möglich, da alle
  Store-Operationen denselben Lock nutzen. Für höhere Last wäre ein
  Read-Write-Lock (`threading.RLock` oder `rwlock`) geeigneter.
- `worker_load_map()` berechnet die Last durch Iteration über alle Tasks —
  O(n) Komplexität. Bei sehr vielen Tasks (>10.000) könnte ein inkrementeller
  Zähler sinnvoller sein.
