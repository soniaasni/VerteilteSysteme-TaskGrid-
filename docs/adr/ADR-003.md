# ADR-003: Worker-Auswahlstrategie

**Status:** Akzeptiert  
**Datum:** 2026-05-26  
**Kontext:** Issue #6 — Worker-Auswahl und Lastverteilung

---

## Kontext

Der Dispatcher muss aus einer vom Namensdienst zurückgegebenen Liste von ACTIVE Workern
(für einen bestimmten Tasktyp) genau einen Worker für die Bearbeitung eines Tasks auswählen.

Die Aufgabenstellung stellt eine explizite Anforderung:

> „Der Dispatcher darf nicht dauerhaft denselben Worker verwenden, wenn mehrere geeignete
> Worker verfügbar sind."

Zusätzlich muss die gewählte Strategie dokumentiert und begründet werden (Bewertungskriterium
Kommunikation & Dokumentation, 15 Punkte).

---

## Betrachtete Alternativen

### 1. Round-Robin
Jeder Worker erhält Tasks reihum in fester Rotation. Pro Tasktyp wird ein unabhängiger
Zähler geführt.

**Vorteile:**
- Deterministisch und vorhersehbar — gut testbar
- Gleichmäßige Verteilung bei homogener Taskdauer
- Kein Overhead: O(1) Selektion, keine Zustandsabfrage nötig
- Erfüllt die Pflichtanforderung (kein dauerhafter Einzelworker) direkt
- Unabhängige Zähler pro Tasktyp verhindern gegenseitige Beeinflussung

**Nachteile:**
- Ignoriert aktuelle Last (`current_load`) — ein langsamer Worker bekommt gleich
  viele Tasks wie ein schneller
- Kann bei sehr unterschiedlicher Taskdauer zu Ungleichgewicht führen

---

### 2. Least-Load
Immer den Worker mit dem niedrigsten `current_load` wählen (Metadatum vom Namensdienst).

**Vorteile:**
- Bessere Lastverteilung bei heterogener Taskdauer
- Nutzt bereits vorhandene `current_load`-Metadaten

**Nachteile:**
- `current_load` kommt vom letzten Heartbeat — kann veraltet sein (Lag)
- Bei mehreren gleichzeitigen Dispatches Race Condition: mehrere Tasks landen
  beim selben "am wenigsten belasteten" Worker bevor sich der Load aktualisiert
- Höherer Implementierungsaufwand für unsicheren Vorteil
- Schlechter testbar (nicht-deterministisch bei gleichem Load)

---

### 3. Random
Zufällige Auswahl aus der Worker-Liste.

**Vorteile:**
- Trivial zu implementieren

**Nachteile:**
- Nicht-deterministisch — schwer reproduzierbar zu testen
- Statistisch können einzelne Worker dauerhaft bevorzugt werden (Clustering)
- Erfüllt die Pflichtanforderung technisch, aber schlecht begründbar

---

### 4. First-Available
Immer den ersten ACTIVE Worker in der Liste nehmen.

**Nachteile:**
- Verletzt die Pflichtanforderung direkt: bei stabiler Worker-Reihenfolge im Namensdienst
  wird dauerhaft derselbe Worker ausgewählt
- Ausgeschlossen.

---

## Entscheidung

**Round-Robin** wurde gewählt.

### Begründung

**1. Pflichtanforderung erfüllt — zuverlässig:**  
Round-Robin garantiert, dass bei `n` verfügbaren Workern nach spätestens `n` Tasks jeder
Worker genau einmal ausgewählt wurde. Die Aufgabenanforderung ist damit strukturell
erfüllt, nicht nur statistisch.

**2. Overhead-Freiheit:**  
Im Gegensatz zu Least-Load wird kein Netzwerkzustand abgefragt oder interpretiert.
Der Namensdienst liefert eine Momentaufnahme der `current_load`-Werte zum Heartbeat-Zeitpunkt
— dieser Wert kann beim Dispatcher-Aufruf bereits Sekunden veraltet sein. Round-Robin
vermeidet diesen Staleness-Fehler vollständig.

**3. Testbarkeit:**  
Deterministisches Verhalten erlaubt exakte Assertions in Tests:
`[w1, w2, w3, w1, w2, w3, ...]`. Randomisierte oder lastbasierte Strategien erfordern
statistische Tests oder aufwändige Mocks.

**4. Korrektheit bei Homogenität:**  
Die Pflicht-Tasktypen (`reverse`, `sum`, `hash`, `upper`, `wait`) haben vergleichbare
und kurze Laufzeiten. Bei homogener Taskdauer ist Round-Robin gleichwertig zu Least-Load.
Ein Wechsel zu Least-Load ist nur bei stark heterogenen Laufzeiten sinnvoll — das ist
in diesem System nicht der Normalfall.

**5. Erweiterbarkeit:**  
`RoundRobinSelector` implementiert eine klare Schnittstelle (`select(task_type, workers)`).
Ein Austausch gegen `LeastLoadSelector` erfordert nur eine andere Klasse — keine Änderung
am Dispatcher-Servicer.

---

## Konsequenzen

**Positiv:**
- Einfache, korrekte Implementierung ohne externe Abhängigkeiten
- Deterministisch testbar (18 Tests, alle grün)
- Aufgabenpflicht strukturell und nachweisbar erfüllt

**Negativ/Akzeptiert:**
- Bei stark unterschiedlicher Taskdauer (z. B. viele `wait`-Tasks neben schnellen
  `reverse`-Tasks) kann Last-Ungleichgewicht entstehen
- Abhilfe falls nötig: Least-Load als Drop-in-Ersatz durch `worker_selector.py`

---

## Implementierung

```python
# src/dispatcher/worker_selector.py
class RoundRobinSelector:
    def __init__(self):
        self._counters = defaultdict(int)  # unabhängig pro Tasktyp
        self._lock = threading.Lock()

    def select(self, task_type, workers):
        if not workers:
            return None
        with self._lock:
            idx = self._counters[task_type] % len(workers)
            self._counters[task_type] += 1
        return workers[idx]
```

Aufruf im Dispatcher:
```python
workers = self._ns_client.lookup_worker(task_type)   # Liste vom Namensdienst
selected = self._selector.select(task_type, workers) # Round-Robin Auswahl
```
