# ADR-005: Timeout-Reaktion und Retry-Strategie

**Status:** Accepted  
**Issue:** #18  
**Datum:** 2026-05-26  
**Entscheider:** soniaasni, Xplosy, Elena7x

---

## Kontext

Wenn ein Worker einen Task akzeptiert hat (DISPATCHED → PROCESSING), aber kein
Ergebnis innerhalb der konfigurierten Frist zurücksendet, muss der Dispatcher
reagieren. Mögliche Ursachen: Worker abgestürzt, überlastet, Netzwerkausfall.

Das Zustandsmodell sieht die Zustände TIMEOUT und RETRYING explizit vor (§5 Aufgabenstellung).

---

## Entscheidung

**Gewählte Strategie: Erneute Einplanung mit konfiguriertem Retry-Limit**

```
DISPATCHED ──timeout──► TIMEOUT ──► RETRYING ──► DISPATCHED  (retry_count < MAX_RETRIES)
                                              └──► FAILED      (retry_count >= MAX_RETRIES)
```

**Ablauf:**
1. Nach `DISPATCH_TIMEOUT_SECONDS` (Standard: 30s) ohne Ergebnis feuert ein `threading.Timer`.
2. Dispatcher liest frischen Task-Zustand aus dem Store.
3. Ist der Task bereits terminal (COMPLETED/FAILED) → Timer-Feuer ignorieren (verspätet).
4. Übergang: DISPATCHED → TIMEOUT → RETRYING, `retry_count` um 1 erhöhen.
5. `retry_count >= MAX_RETRIES` (Standard: 3): RETRYING → FAILED, fertig.
6. Sonst: Task erneut in Queue einreihen. Dispatch-Loop wählt nächsten Worker (Round-Robin).

**Konfigurierbare Parameter (Umgebungsvariablen):**

| Variable | Standard | Bedeutung |
|----------|---------|-----------|
| `DISPATCH_TIMEOUT_SECONDS` | 30 | Sekunden bis Timeout nach Dispatch |
| `MAX_RETRIES` | 3 | Max. Wiederholungen pro Task |

---

## Betrachtete Alternativen

### A: Sofort FAILED beim ersten Timeout
- Einfach, aber keine Fehlertoleranz. Ein kurzer Netzwerkausfall würde Task dauerhaft
  vernichten. Ungeeignet für produktiven Betrieb.

### B: Unbegrenzte Retries
- Task kann nie FAILED werden durch Timeout. Hängende Tasks blockieren Ressourcen
  dauerhaft. Kein Sicherheitsnetz gegen dauerhaft ausgefallene Worker.

### C: Direktweiterleitung an anderen Worker (ohne RETRYING-Zustand)
- Umgeht den definierten Zustandsgraphen. Der RETRYING-Zustand aus §5 wäre nicht
  genutzt, was gegen die Aufgabenstellung verstößt.

### D: Gewählte Strategie (Retry mit Limit) ✓
- Nutzt alle vorgeschriebenen Zustände (TIMEOUT, RETRYING) aus §5.
- Balanciert Fehlertoleranz (temporäre Ausfälle werden überbrückt) mit Sicherheit
  (bei dauerhaftem Ausfall endet der Task nach MAX_RETRIES in FAILED).
- Retry an beliebigem Worker — Round-Robin-Selektor kann einen anderen Worker wählen.
- Vollständig konfigurierbar ohne Code-Änderung (Env-Variablen).

---

## Konsequenzen

**Positiv:**
- Temporäre Worker-Ausfälle werden transparent überbrückt.
- Tasks bleiben im System nachvollziehbar (TIMEOUT/RETRYING-Verlauf sichtbar).
- Konfigurierbar für verschiedene Deployment-Umgebungen.
- Keine doppelte Verarbeitung: verspätete Ergebnisse vom alten Worker landen auf
  einem terminalen Task (FAILED) und werden ignoriert (Idempotenz §5).

**Negativ:**
- Ein Task kann bis zu `MAX_RETRIES × DISPATCH_TIMEOUT_SECONDS` im System verbleiben
  bevor er FAILED wird (bei MAX_RETRIES=3, TIMEOUT=30s → max. 90s).
- Kein intelligentes Backoff — alle Retries mit demselben Timeout-Wert.
