# ADR-006: Monitoring-Schnittstelle als HTTP-Endpoint (Issue #20)

**Status:** Akzeptiert  
**Issue:** #20  
**Datum:** 2026-05-26  
**Entscheider:** soniaasni, Xplosy, Elena7x

---

## Kontext

Issue #20 verlangt eine Monitoring-Schnittstelle, die mindestens neun Felder zurückliefert:

```json
{
  "aktive_worker": 3,
  "unterstützte_tasktypen": ["sum", "reverse", "hash"],
  "offene_tasks": 2,
  "laufende_tasks": 1,
  "abgeschlossene_tasks": 47,
  "fehlgeschlagene_tasks": 2,
  "durchschnittliche_bearbeitungszeit_ms": 85,
  "anzahl_timeouts": 1,
  "anzahl_retries": 3
}
```

Die Aufgabenstellung lässt drei Umsetzungsformen zu: HTTP/REST-Endpoint, UDP-Nachricht
oder CLI-Ausgabe. Die Schnittstelle muss über `docker-compose` erreichbar sein (Port
exponiert).

Das System kommuniziert intern ausschließlich über gRPC/Protobuf. Der Dispatcher
besitzt bereits einen gRPC-Stub `GetStatus` (DispatcherService), der bisher
unimplementiert war. Das gemeinsame Proto-Schema (`taskgrid.proto`) ist auf
Elena-Kompatibilität ausgelegt — Änderungen daran können die Worker-Integration
destabilisieren.

---

## Entscheidung

**Gewählte Strategie: HTTP/REST-Endpoint auf Port 8080, als Daemon-Thread im Dispatcher-Prozess**

Der Dispatcher startet beim Hochfahren einen zusätzlichen HTTP-Server-Thread
(`HttpStatusServer`) auf Port `STATUS_HTTP_PORT` (Standard: 8080). Ein einziger
Endpunkt `GET /status` liefert alle neun Pflichtfelder als JSON.

Parallel dazu wird der vorhandene gRPC-`GetStatus`-Stub implementiert: Er nutzt
dieselbe `StatusCollector`-Klasse und gibt die Daten als komprimiertes JSON im
`details`-Feld des `StatusResponse` zurück — so ist Monitoring auch für gRPC-Clients
möglich.

**Architektur:**

```
Dispatcher-Prozess
├── gRPC-Server (Port 50051)       ← bestehend
│     └── GetStatus()              ← jetzt implementiert via StatusCollector
├── HTTP-Server (Port 8080)        ← neu, Daemon-Thread
│     └── GET /status              ← JSON mit allen 9 Feldern
└── StatusCollector                ← gemeinsame Datenquelle
      ├── TaskStore (in-memory)
      └── NamensdienstClient (gRPC-Lookup für aktive Worker)
```

**Datenquellen pro Feld:**

| Feld | Quelle |
|------|--------|
| `aktive_worker` | Namensdienst: `LookupWorker` für jeden bekannten Task-Typ, Worker-IDs dedupliziert |
| `unterstützte_tasktypen` | TaskStore: alle eindeutigen `task_type`-Werte aus je einem Task |
| `offene_tasks` | TaskStore: Anzahl Tasks mit Status `QUEUED` |
| `laufende_tasks` | TaskStore: Anzahl Tasks mit Status `DISPATCHED`, `PROCESSING` oder `RETRYING` |
| `abgeschlossene_tasks` | TaskStore: Anzahl Tasks mit Status `COMPLETED` |
| `fehlgeschlagene_tasks` | TaskStore: Anzahl Tasks mit Status `FAILED` oder `TIMEOUT` |
| `durchschnittliche_bearbeitungszeit_ms` | TaskStore: Mittelwert von `(timestamp_completed − timestamp_dispatched) × 1000` über alle COMPLETED-Tasks mit gültigen Zeitstempeln |
| `anzahl_timeouts` | TaskStore: Summe aller `task.retry_count`-Werte (jeder Retry wurde durch einen Timeout ausgelöst) |
| `anzahl_retries` | Identisch mit `anzahl_timeouts` (gleiche Berechnungsgrundlage) |

**Konfiguration (Umgebungsvariablen):**

| Variable | Standard | Bedeutung |
|----------|---------|-----------|
| `STATUS_HTTP_PORT` | 8080 | Port des HTTP-Monitoring-Endpoints |

## Betrachtete Alternativen

### A: Erweiterung des gRPC-Protokolls (`StatusResponse` mit allen 9 Feldern)

Das Proto-Schema müsste um sieben neue Felder erweitert werden (aktive_worker,
unterstützte_tasktypen als repeated string, avg_ms, timeouts, retries …).
Anschließend müssten beide Proto-generierten Python-Dateien (`taskgrid_pb2.py`,
`taskgrid_pb2_grpc.py`) neu generiert werden.

**Abgelehnt**, weil:
- Jede Proto-Änderung birgt Kompatibilitätsrisiken mit Elenas Worker-Code, der
  seinen eigenen generierten Proto-Stub mitbringt.
- Die Aufgabenstellung erlaubt HTTP/REST ausdrücklich — es gibt keinen Grund, unnötige
  Risiken einzugehen.
- Proto-Felder sind streng typisiert: eine Liste von Strings (`repeated string`) für
  Task-Typen wäre korrekt, aber das Feld `details` als JSON-String ist flexibler
  und erweiterbar ohne erneute Generierung.

### B: UDP-Broadcast

Der Dispatcher sendet periodisch Status-Pakete per UDP an einen konfigurierten
Monitoring-Host.

**Abgelehnt**, weil:
- Verbindungslos: kein garantierter Empfang, kein Request-Response-Modell.
- Monitoring-Tools (Prometheus, curl, Browser) unterstützen kein UDP.
- Deutlich mehr Implementierungsaufwand (Serialisierung, Empfänger-Seite) ohne
  Mehrwert gegenüber HTTP.
- Docker-Port-Exposition funktioniert mit UDP zwar technisch, ist aber ungewöhnlich
  und schlechter dokumentiert.

### C: CLI-Skript (separates Python-Skript, das per `docker exec` aufgerufen wird)

Ein Skript liest den Task-Store und gibt Status auf stdout aus.

**Abgelehnt**, weil:
- Erfordert `docker exec`-Zugriff auf den laufenden Container — kein echtes
  Netzwerk-Monitoring, nicht von außen erreichbar ohne SSH/exec-Zugang.
- Kein dauerhaft lauschender Endpoint → kann nicht in ein Monitoring-Dashboard
  (Prometheus, Grafana, einfacher Browser) integriert werden.
- Die Anforderung „über docker-compose erreichbar (Port im compose-File exponiert)"
  impliziert einen Netzwerk-Endpoint, kein CLI-Skript.

### D: Separater Monitoring-Container (eigener Microservice)

Ein eigenständiger Dienst fragt den Dispatcher per gRPC ab und stellt HTTP bereit.

**Abgelehnt**, weil:
- Erfordert IPC zwischen Dispatcher und Monitoring-Container (gRPC-Aufruf oder
  gemeinsamer Datenspeicher) — erhöht die Komplexität erheblich.
- Der Dispatcher besitzt bereits alle Daten in-memory; ein separater Container
  bräuchte entweder einen gemeinsamen Redis/DB oder einen gRPC-Aufruf zurück an
  den Dispatcher.
- Unverhältnismäßiger Aufwand für eine Monitoring-Schnittstelle im Studienkontext.

### E: Gewählte Strategie (HTTP-Daemon-Thread im Dispatcher) ✓

- Kein Proto-Eingriff, keine Elena-Kompatibilitätsrisiken.
- Alle neun Pflichtfelder frei als JSON — keine Schema-Beschränkungen.
- Universell testbar mit `curl http://localhost:8080/status` oder im Browser.
- Docker-Port 8080 trivial zu exponieren (`ports: - "8080:8080"`).
- `StatusCollector` als eigenständige Klasse ist vollständig unit-testbar (kein
  laufender HTTP-Server nötig).
- Geteilt zwischen HTTP-Endpoint und gRPC-`GetStatus` → keine Logik-Duplizierung.
- Daemon-Thread stirbt automatisch mit dem Dispatcher-Prozess — kein separater
  Shutdown-Mechanismus nötig.

## Implementierungsdetails

### StatusCollector (`src/dispatcher/status_collector.py`)

Kapselt die gesamte Aggregationslogik. Wird bei jedem `GET /status`-Aufruf frisch
berechnet (kein Caching), um immer den aktuellen Stand zurückzugeben. Nimmt
`TaskStore` und `NamensdienstClient` als Abhängigkeiten entgegen — vollständig
mit Mocks testbar.

Besonderheit bei aktiven Workern: Da das Proto kein „Alle Worker auflisten"-RPC
kennt, werden alle im TaskStore vorhandenen Task-Typen gesammelt und für jeden
Typ ein `LookupWorker`-Aufruf am Namensdienst gemacht. Die zurückgegebenen
Worker-IDs werden in einem Set dedupliziert, sodass Worker die mehrere Task-Typen
unterstützen nur einmal gezählt werden.

### HttpStatusServer (`src/dispatcher/http_status_server.py`)

Nutzt Pythons eingebautes `http.server`-Modul (keine zusätzliche Abhängigkeit).
Lauscht auf `0.0.0.0` damit der Port vom Docker-Host erreichbar ist. Loggt
eingehende Requests auf DEBUG-Level über das bestehende Logging-System (Issue #19).

### gRPC GetStatus

Der vorhandene Stub in `servicer.py` wird implementiert: Er ruft
`StatusCollector.get_status()` auf und packt das Ergebnis als JSON-String in
`StatusResponse.details`. Die Felder `queued_tasks` und `active_workers` werden
direkt befüllt (Proto-Schema-konform). Damit ist die gRPC-Schnittstelle für
bestehende gRPC-Clients nutzbar ohne Proto-Erweiterung.

## Konsequenzen

**Positiv:**
- Alle neun Monitoring-Felder aus Issue #20 vollständig abgedeckt.
- Zero-Dependency: kein Flask, kein FastAPI — nur Python-Stdlib.
- Einfache Integration in CI: `curl http://localhost:8080/status` reicht zum
  Smoke-Test.
- Proto und Elena-Worker-Kompatibilität vollständig erhalten.
- `StatusCollector` isoliert und mit 11 Unit-Tests abgedeckt.

**Negativ:**
- Status wird bei jedem Request neu berechnet (kein Cache). Bei sehr vielen Tasks
  im Store und vielen Task-Typen entstehen mehrere Namensdienst-Lookups pro Anfrage.
  Für den Studienkontext unbedeutend; in Produktion wäre ein TTL-Cache sinnvoll.
- `anzahl_timeouts` und `anzahl_retries` liefern denselben Wert, da jeder Retry
  durch genau einen Timeout ausgelöst wird. Falls künftig Retries ohne Timeout
  (z.B. durch Worker-Ablehnung) eingeführt werden, müssen beide Zähler getrennt
  geführt werden.
- HTTP-Server läuft ohne TLS/Authentifizierung — ausreichend für internes
  Docker-Netz, nicht für öffentlich exponierte Deployments geeignet.
