# ADR-004: Speicherung von Tasks und Ergebnissen (In-Memory vs. Persistent)

**Status:** Akzeptiert  
**Issue:** #21 / #13 / #16  
**Datum:** 2026-05-26  
**Entscheider:** soniaasni, Xplosy, Elena7x

---

## Kontext

Der Dispatcher muss alle Tasks — inklusive Zustand, Payload, Ergebnis,
Zeitstempel und Retry-Zähler — während ihrer Lebensdauer im System speichern.
Ein Client kann das Ergebnis eines Tasks erst abfragen, wenn der Worker die
Verarbeitung abgeschlossen hat (`ReturnResult`). Der Dispatcher ist damit der
einzige persistente Speicherort für Task-Zustand und Ergebnis im System.

Die Aufgabenstellung (§8) gibt vor:
> „Für die Übergabe von Aufgaben und Ergebnissen dürfen keine gemeinsamen
> Dateisysteme oder Datenbanken verwendet werden."

Außerdem gilt (§4.1):
> Worker-Registrierungen werden nur im RAM des Namensdiensts gehalten.
> Bei einem Neustart des Namensdiensts registrieren sich Worker erneut.

Damit ist die Grundlinie des Systems klar: **kein persistenter Shared State**
zwischen Komponenten. Die Frage ist, ob der Dispatcher intern eine Datenbank,
ein externes Cache-System oder reinen RAM nutzt.

---

## Entscheidung

**Gewählte Strategie: In-Memory-Speicherung im Dispatcher-Prozess**

Alle Tasks werden in einem Python-`dict` im RAM des Dispatcher-Prozesses
gehalten (`TaskStore`). Kein externer Speicher, keine Datenbankverbindung.
Logs werden über ein Docker-Volume persistiert — Task-Daten nicht.

```
Dispatcher-Prozess
└── TaskStore
      └── dict[task_id → Task]   (RAM)

Docker-Volume: /app/logs          (nur Logs, keine Task-Daten)
```

**Datenstruktur pro Task:**

| Feld | Typ | Bedeutung |
|------|-----|-----------|
| `task_id` | str (int32-kompatibler Zähler) | Eindeutige ID |
| `task_type` | str (max. 32 Zeichen) | Verarbeitungstyp |
| `payload` | str (max. 1024 Zeichen) | Eingabedaten |
| `result` | str (max. 1024 Zeichen) | Ergebnisdaten oder Fehlermeldung |
| `status` | TaskState (Enum) | Aktueller Zustand (8 Zustände) |
| `timestamp_created` | int (Unix) | Erstellungszeitpunkt |
| `timestamp_dispatched` | int (Unix) | Zeitpunkt des Dispatchens |
| `timestamp_completed` | int (Unix) | Zeitpunkt des Abschlusses |
| `retry_count` | int | Anzahl bisheriger Wiederholungsversuche |
| `assigned_worker` | str (max. 64 Zeichen) | Zuletzt zugewiesener Worker |

## Betrachtete Alternativen

### A: Relationale Datenbank (z.B. SQLite, PostgreSQL)

Tasks werden in einer SQL-Tabelle persistiert. Bei Dispatcher-Neustart bleiben
alle Tasks erhalten.

**Abgelehnt**, weil:
- Die Aufgabenstellung (§8) verbietet explizit gemeinsame Datenbanken für die
  Übergabe von Aufgaben und Ergebnissen. Eine interne Datenbank des Dispatchers
  wäre technisch erlaubt, aber unnötige Komplexität.
- Erfordert eine zusätzliche Abhängigkeit (SQLAlchemy, psycopg2 o.ä.) und einen
  separaten Datenbank-Container in `docker-compose.yml`.
- Datenbankzugriffe führen Latenzen und mögliche Verbindungsfehler ein — für
  kurze Task-Laufzeiten ein unnötiger Overhead.
- Migration, Schema-Versionierung und Connection-Pooling wären weitere Baustellen
  ohne erkennbaren Nutzen im Studienkontext.
- Das System ist für kurze Laufzeiten (Übungsabgabe, Smoke-Tests) ausgelegt —
  Durability über Container-Neustarts hinweg ist keine Anforderung.

### B: Key-Value-Store (z.B. Redis)

Tasks werden in Redis gespeichert. Erlaubt optionale Persistenz (AOF/RDB)
und ist netzwerkfähig — mehrere Dispatcher-Instanzen könnten denselben Store nutzen.

**Abgelehnt**, weil:
- Erfordert einen weiteren Container in `docker-compose.yml` und erhöht die
  Systemkomplexität erheblich.
- Einführt Netzwerklatenz bei jedem Lese-/Schreibzugriff.
- Die Aufgabenstellung sieht genau einen Dispatcher vor (keine horizontale
  Skalierung des Dispatchers als Anforderung) — der Haupt-Vorteil von Redis
  (geteilter State) ist damit wertlos.
- Serialisierung/Deserialisierung der `Task`-Objekte (Pickle oder JSON)
  erfordert zusätzlichen Code und birgt Kompatibilitätsrisiken.

### C: Dateibasierter Speicher (JSON-Datei oder SQLite-Datei)

Tasks werden in einer lokalen Datei persistiert. Bei Neustart des Containers
bleiben Tasks erhalten (wenn über Docker-Volume gemountet).

**Abgelehnt**, weil:
- Dateizugriffe erfordern explizite Synchronisation (Locking auf Dateiebene)
  zusätzlich zum bereits vorhandenen In-Memory-Lock — doppelte Komplexität.
- Atomares Schreiben ohne Datenverlust (Crash mid-write) erfordert
  Write-Ahead-Logging oder temporäre Dateien — komplexer als nötig.
- Die Aufgabenstellung sieht §8 vor: Volumes nur für Logs erlaubt. Ein Volume
  für Task-Daten würde dieser Vorgabe widersprechen.

### D: In-Memory mit optionalem Snapshot (hybride Lösung)

Tasks im RAM, periodischer Dump auf Disk als JSON-Snapshot. Bei Neustart
optional wiederherstellbar.

**Abgelehnt**, weil:
- Erhöht die Implementierungskomplexität ohne klare Anforderung.
- Ein Dispatcher-Neustart ist im Normalbetrieb selten und im Fehlerfall akzeptabel
  (Tasks werden neu gestellt, Worker re-registrieren sich).
- Kein Mehrwert gegenüber reinem In-Memory für den definierten Einsatzbereich.

### E: Gewählte Strategie (reines In-Memory) ✓

- Direkte Anforderungserfüllung: §8 verbietet Shared-Storage für Task-Daten —
  In-Memory ist die naturgemäße Umsetzung.
- Keine zusätzlichen Abhängigkeiten, kein externer Dienst.
- Zugriffe in O(1) — Python-dict-Lookup ist schneller als jeder DB-Roundtrip.
- Thread-Sicherheit durch einen einzigen `threading.Lock` im `TaskStore`
  (ADR-007: Fine-Grained Locking).
- Lebensdauer der Task-Daten entspricht exakt der Laufzeit des Dispatchers —
  sauber definiertes Ownership ohne Altlasten über Neustarts hinweg.

## Implementierung

```python
# src/dispatcher/task_store.py
class TaskStore:
    def __init__(self) -> None:
        self._tasks: Dict[str, Task] = {}   # reines Python-dict im RAM
        self._lock = threading.Lock()        # ein Lock für alle Operationen

    def add(self, task: Task) -> None:
        with self._lock:
            self._tasks[task.task_id] = task

    def get(self, task_id: str) -> Optional[Task]:
        with self._lock:
            return self._tasks.get(task_id)

    def update(self, task: Task) -> None:
        with self._lock:
            self._tasks[task.task_id] = task

    def all_tasks(self) -> List[Task]:
        with self._lock:
            return list(self._tasks.values())   # Snapshot unter Lock
```

**Docker-Compose (docker-compose.yml):**
```yaml
volumes:
  logs:                            # NUR für Logs — KEIN Volume für Task-Daten
dispatcher:
  volumes:
    - logs:/app/logs               # Logs persistieren (§8: nur für Logs erlaubt)
```

## Konsequenzen

**Positiv:**
- Null-Latenz bei Zugriffen — kein Netzwerk, kein Disk-I/O.
- Kein zusätzlicher Container, keine externe Abhängigkeit.
- Einfache Fehlerbehandlung: Store ist immer verfügbar solange der Prozess läuft.
- Vollständig mit Unit-Tests abdeckbar ohne Datenbankaufbau (95 Tests, alle grün).
- Konform mit Aufgabenstellung §8 (keine gemeinsamen Datenbanken/Dateisysteme
  für Task-Übergabe).

**Negativ/Akzeptiert:**
- Bei Dispatcher-Neustart gehen alle laufenden und ausstehenden Tasks verloren.
  Clients müssen Tasks erneut senden. Dies ist für den Studienkontext akzeptabel —
  Durability ist keine Anforderung.
- Speicherwachstum bei sehr langem Betrieb: Tasks werden nicht automatisch gelöscht
  (kein TTL/Eviction). In Produktion wäre ein Eviction-Mechanismus für terminale
  Tasks sinnvoll.
- Keine Horizontal-Skalierung des Dispatchers möglich (kein Shared State zwischen
  mehreren Dispatcher-Instanzen). Für die Anforderungen des Projekts irrelevant.
